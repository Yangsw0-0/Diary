# 架构审查处理记录（2026-11-18）

本记录回应对模块化、对象边界和偏好存储的只读审查。判断依据是当前 Diary 只有日记、标签两个主工作区，以及设置页；本次发布目标是完成帮助说明并保持现有保存和导航行为可靠。

## 本次采纳

| 建议 | 处理 | 理由 |
| --- | --- | --- |
| 设置页与历史导航不一致 | 在设置页点击“返回上一页面”先关闭设置；“返回下一页面”在设置页禁用，并增加回归测试 | 这是可复现的用户行为问题。设置暂不占用历史项；关闭后原页面和原历史仍在 |
| Feature 直接依赖应用外壳 | 将共用的 `NavigationContext` 移到 `src/shared/`，应用外壳和 feature 同向依赖共享接口 | 去掉 feature 对 `src/app/` 的反向导入，同时保留既有导航能力 |
| 标签 feature 直接导入外部链接实现 | 为标签界面定义 `ExternalLinkPort`，在 `bootstrap` 注入具体实现 | UI 不再绑定 Tauri/浏览器打开方式 |
| 标签组件自行读取 localStorage | 在组合根创建 `TagVisibility`，通过 provider 传入标签界面 | 存储初始化由装配层负责，组件只使用显隐接口 |
| 索引依赖具体显隐类 | `TagIndex.listGroups` 改依赖 `TagVisibilityPolicy` | 索引只需要 `isShown`，可用独立策略测试 |

## 暂缓与保留

| 建议 | 判断 |
| --- | --- |
| 把所有页面统一为可注册模块，并改造泛型 `NavigationView` | 方向有价值，但现有日记导航还包含草稿保存守卫、标签小节定位和滚动恢复。现在把 view 改为 `unknown` 会丢失类型保证，也可能破坏历史行为。新增第三个真正的主工作区时，以具体用例设计模块契约及跨模块测试。 |
| 设置页立即做成 FeatureModule 或历史 route | 本次用“返回先关闭设置”修正实际缺陷。设置是临时的全屏面板，当前产品没有要求用“前进”重新进入设置；强行纳入日记/标签的双栏模块契约会增加特殊分支。若以后需要设置页历史，再统一页面模型。 |
| 将 `DiarySession` / `DiaryService` 完整拆分 | 类较大且列表可能多次渲染，值得后续分析。但没有性能测量或独立变化需求，不宜在帮助功能发布时重写保存队列、冲突处理和工作区切换。后续先测量列表更新开销，再按真实边界拆分。 |
| `TagService.getSections` 读取时不得修索引 | 当前读取原日记时修正索引可处理外部修改。如果改成显式刷新而没有新的变更检测，标签页可能显示过期内容，暂保留现状。 |
| 统一所有偏好到泛型 `get<T>/set<T>` | Rust 工作区设置、本机标签显隐和会话内缩放的生命周期不同。一个无运行时校验的泛型存储接口不能保证迁移安全。若以后提供统一重置或跨设备同步，再设计有版本、校验和迁移的具体偏好模型。 |
| `ThemePalette` 预设、`TagIndex` 补全查询、文件顺序等均抽接口或类 | 当前都是同一层内的小范围数据/查询，进一步拆分未体现独立变化原因。保留简单实现，避免为了类数量而抽象。 |

本次不改变日记文件格式、用户日记、附件或保存协议。
